# RAG 管线

年报问答的状态机。检索交给 `retrieval/`，模型调用交给 `providers/`，
这一层只负责编排和纠错决策。

```
analyze ─┬─ in_corpus ────→ retrieve → grade ─┬─ correct ─→ generate
         │                                     └─ 其余 ────┐
         └─ out_of_corpus ──────────────────────────────→ search_web → generate
```

## 🚀 使用

```bash
python main.py                          # 交互模式，支持多轮追问
python main.py "五粮液2024年营收多少"      # 单次提问
```

```python
from rag import app, cite

result = app.invoke({"question": "宁德时代2024年研发费用", "chat_history": []})
print(result["generation"])
print(cite(result["documents"]))
```

## 🧩 各节点

### analyze —— 查询分析

做两件事：把追问补全成自包含的查询，以及抽出公司和年份。

```
用户: 宁德时代2025年的研发费用是多少
用户: 那2024年的呢？        → 宁德时代2024年的研发费用是多少
用户: 五粮液同期呢？         → 五粮液2024年的研发费用是多少
```

抽出的公司和年份会**先与索引里实际存在的组合比对**，对得上才作为过滤条件，
对不上就直接判定越界。

### route_scope —— 范围路由

公司或年份不在语料内时，**跳过整个检索和评分环节**。

答案在 `analyze` 阶段就已经确定了——语料里没有茅台，检索再怎么跑也只能返回五粮液的内容，
评分器也必然全部拒绝。这一跳省掉一次检索加五次 LLM 评分：

| 查询 | 加路由前 | 加路由后 |
|---|---|---|
| 茅台2024年的营业收入 | 18.9 s | **2.2 s** |

省下的不只是调用。范围检查用 `load_metadata()` 只读 `units.jsonl`，
不走 `get_retriever()`——否则为了查个范围要先把 1.2GB 的嵌入模型和整个索引加载一遍，
这在越界路径上是纯浪费。

校验的是 **(公司, 年份) 组合**而不是两个独立集合。目前四个组合都齐，
但语料不齐时（比如只有五粮液 2024 和宁德时代 2025），分开校验会让
"五粮液 2025"这种不存在的组合蒙混过关。

越界时的答复会带上覆盖范围，而不是干巴巴地说找不到：

```
抱歉，语料中没有茅台的年报。
目前收录的是：五粮液 2024/2025年报、宁德时代 2024/2025年报。
```

### retrieve —— 混合检索

调 `HybridRetriever.search()`，返回 5 个父块。文档以 `Document` 对象在图里流动，
元数据一路带到最后用于引用标注——只传正文字符串的话，"这个数字出自 2024 年报第 61 页"
就无从说起了。

### grade —— CRAG 的检索评估器

两级判定，这是整个管线里最关键的设计。

**第一级用重排分数**。按当前的百炼重排 API 实测标定：

| 查询类型 | 最高重排分 |
|---|---|
| 语料内可答 | 0.936 – 0.999 |
| 完全无关（天气、菜谱） | 0.0038 – 0.0488 |
| 同域但语料外 | 0.245 – 0.741 |

低于 `IRRELEVANT = 0.1` 直接判失败，**一次 LLM 调用都不花**。

**换重排模型必须重新标定这个阈值。** 本地 Qwen3-Reranker 的无关区间是
0.0003–0.0025，比 API 低整整一个量级，直接套用会让阈值失去意义。

**第二级用 LLM**，因为重排分数判断的是话题相关性，不是事实可答性。
"茅台2024年的营业收入"配上五粮液的收入表，本地重排器给 **0.9161**、
API 给 0.3408——话题上确实相关，但拿它生成答案就是编造。
所以中间地带要过一遍 LLM 做公司和年份的核对，
评分 prompt 里明确要求跨公司、跨年份一律判不相关。

实测茅台那一问，LLM 评分器 5/5 全拒，最终回答"没有找到依据"。

三条路径按 CRAG 原论文：全部通过是 `correct`，部分通过是 `ambiguous`（补一次联网），
全不通过是 `incorrect`（只能靠联网）。

### search_web —— 纠正动作

没配 `TAVILY_API_KEY` 时打印警告后继续，不会让整轮问答失败。

### generate —— 生成

上下文按 `[1] 公司 年份 · 章节 · 页码` 编号，要求模型引用编号。
prompt 明确禁止编造和估算，上下文不足时要说明缺什么而不是拿相近数据搪塞。

## ⚠️ 用重写后的查询，不是原始提问

`grade` 和 `generate` 都用 `state["query"]` 而非 `state["question"]`。
追问"那2024年的呢？"本身没有主语，拿它去评分等于让模型盲判，拿它去生成
会得到"请问您指的是哪一项数据？"这种反问。`state["question"]` 只保留原文备查。

## ⚠️ 结构化输出必须用 json_schema

LangChain 的 `with_structured_output` 默认走 function calling，在 Qwen 上会
**间歇性陷入生成循环**——实测有一次吐满 32768 token 才以 `LengthFinishReasonError` 退出，
而同样的输入用裸 JSON prompt 只要 28 token。它不是稳定复现的，所以更危险。

`json_mode` 被 DashScope 直接拒绝（400）。只有 `json_schema` 三次测试全稳，0.7–0.8 秒。

除此之外还加了两层兜底：`max_tokens=512` 封顶，以及 `analyze` 失败时退回用原始提问、
`grade` 失败时保守判为不相关。

## 🤖 模型分工

| 环节 | 模型 | 理由 |
|---|---|---|
| 查询分析 | `qwen-flash` | 每轮一次，任务简单 |
| 文档评分 | `qwen-flash` | 每轮 5 次，并发调用，便宜要紧 |
| 答案生成 | `qwen-plus` | 每轮一次，质量要紧 |

评分是 5 篇并发跑的，否则串行会把延迟拖到不可接受。

## ⏱️ 延迟

| 路径 | 耗时 |
|---|---|
| 越界（被 `route_scope` 拦下） | 2.2 s |
| 正常问答 | 约 20 s |

正常路径里检索占 1.5 秒，其余是三类 LLM 调用和本地嵌入模型的加载（约 10 秒，仅首次）。

## ⚙️ 可调参数

| 位置 | 参数 | 默认 | 说明 |
|---|---|---|---|
| `nodes.py` | `TOP_K` | 5 | 送进评分和生成的父块数 |
| `nodes.py` | `IRRELEVANT` | 0.1 | 低于此分直接判检索失败 |
| `chains.py` | `GRADER_MODEL` | `qwen-flash` | 分析和评分用的模型 |
| `chains.py` | `GENERATOR_MODEL` | `qwen-plus` | 生成用的模型 |
