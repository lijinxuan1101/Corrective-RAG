# ② 清洗与切块

把 `data/markdown/*.md` 清洗后切成带元数据的 `Document` 列表。

```
preprocess.py       清洗：去页眉页脚、还原勾选框、合并跨页表格
splitter.py         切块：按标题层级切分 + 附加元数据
inspect_chunks.py   质检：统计指标 + 关键词抽样
```

## 🚀 用法

```python
from doc_parsing import load_all

documents = load_all()                      # 默认读 data/markdown/
documents = load_all("data/md_us")
```

```bash
python doc_parsing/chunking/inspect_chunks.py              # 统计
python doc_parsing/chunking/inspect_chunks.py 货币资金       # 关键词抽查
python doc_parsing/chunking/inspect_chunks.py 研发投入 -n 3
```

## 🧹 清洗 `preprocess.py`

`clean_markdown(text) -> (cleaned, stats)`，处理 MinerU 输出里四类会污染检索的内容。

**页眉页脚** — 每页重复的 `宜宾五粮液股份有限公司 2024 年度报告全文` 和孤立的页码数字。页眉文案各家公司不同，按"出现在半数以上页面的首行"自动推断，不必为每家硬编码。

**私有区字符** — `U+F052` 出现 **744 次**，是 Wingdings 字体透传出来的勾选框。年报里满是 `□适用 ☑不适用`，不还原成 ☑ 的话 LLM 看到的是乱码，**无法判断选中的是哪一项**。

**跨页表格** — 共 **162 处**。表格跨页时 MinerU 会把续表当成新表：首行数据行被当作表头，后面还多发一条 `| --- |` 分隔行，导致该块丢失真正的列名。删掉分隔行即可让续表并回上一页的表尾。

```markdown
<!-- 修复前：银行存款那行被当成了表头，列名"项目/期末余额/期初余额"丢失 -->
| 银行存款 | 78,907,591,498.82 | 74,892,248,621.63 |
| --- | --- | --- |
| 其他货币资金 | 202,456,023.63 | 264,472,639.86 |
```

**图片引用** — 指向 MinerU 内部 blob 的 `![Image block](doc:.../block:1)`，链接无法解析，纯噪声。

**标题层级** — MinerU 把 **2317 个标题一律输出成 `##`**，层级信息全部丢失。后果很严重：`（2）按坏账计提方法分类披露` 在一份年报里出现 14 次，分属应收票据、应收账款、合同资产、其他应收款，还有母公司报表里的同名章节，检索时完全无法区分。

年报遵循中文公文编号体例，据此可以还原深度：

| 编号形式 | 深度 | 数量 |
| --- | --- | --- |
| `第X节` | 2 | 39 |
| `一、二、` | 3 | 387 |
| `（一）（二）` | 4 | 59 |
| `1、2、` | 5 | 916 |
| `（1）` `1）` `①` | 6 | 885 |

无编号标题（`致股东的信`、`以摊余成本计量的金融资产`）挂在最近一个编号标题之下，这样同级兄弟能获得相同深度，不会越嵌越深。`□适用 ☑不适用` 是被 MinerU 误判成标题的正文，降级处理。

页码标记会**保留**，供切块阶段提取元数据。

## ✂️ 切块 `splitter.py`

先用 `MarkdownHeaderTextSplitter` 按 `#`/`##`/`###` 切（`strip_headers=False`，让标题留在正文里），再按需二次切分。过程中解决了三个直接影响检索质量的问题。

**碎块** — 年报有大量只含一行标题的小节（如 `## 六、税项` 后面紧跟另一个标题），逐节成块会让 17% 的块短于 30 字符。`_coalesce()` 先把相邻小节聚合到接近 `CHUNK_SIZE` 再切，降到 2%。

**表格丢表头** — 长表格被二次切分后，续块只剩数据行，检索命中时无从判断列含义。`_carry_table_header()` 自动补回表头，把这类块从 146 个降到 3 个。

**HTML 表格破碎** — 按字符切会从 `<td rowspan="2">` 中间断开。417 个 HTML 表格中最大的也只有 4.8k 字符，远低于 embedding 上限，因此 `_segment()` 让**每个表格整块保留、单独成块**并附上章节路径。表格前后的 `单位:元`、`□适用 ☑不适用` 等短句会并入表格块，既消除碎片又保住了量纲说明。

## 🏷️ 元数据

| 字段 | 说明 | 用途 |
| --- | --- | --- |
| `company` / `year` | 从文件名解析（`五粮液2024年报.md`） | 跨文档对比时按元数据过滤 |
| `source` | 源文件名 | 溯源 |
| `section` | 章节路径面包屑 | 让 LLM 知道这段属于哪张报表 |
| `page_start` / `page_end` | 页码范围 | 答案标注出处页码 |

得益于层级还原，面包屑能区分同名章节：

```
第八节 财务报告 > 七、合并财务报表项目注释 > 5、应收账款 > （2）按坏账计提方法分类披露
第八节 财务报告 > 十八、母公司财务报表主要项目注释 > 1、应收账款 > （2）按坏账计提方法分类披露
```

## 🔗 上下文拼接

向量库只嵌入 `page_content`，**元数据字段不参与检索**。而年报指代密度极高——"本公司"、"报告期内"、"期末余额 127,398,915,484.11"，块脱离上下文后无从判断是谁家哪一年的哪张表。

因此每个块在嵌入前会拼上一行上下文：

```
五粮液 2024年报 | 第十节 财务报告 > 七、合并财务报表项目注释 > 1、货币资金

##### 1、货币资金
| 项目 | 期末余额 | 期初余额 |
...
```

这是 Contextual Retrieval 的低成本版本——用模板代替 LLM 生成，省掉 1341 次调用。需要关闭时传 `load_all(contextualize=False)`。

## 🧬 嵌入单元 `indexing.py`

`build_embedding_units(documents)` 把「用于嵌入的文本」与「返回给 LLM 的文本」解耦。

一张 20 行的表压成单个向量后，查询"货币资金期末余额"要和其余 19 行抢这个向量的表达能力，结果被平均稀释。所以表格会**额外拆出行级单元**单独嵌入，命中后通过 `parent_id` 取回完整父块交给 LLM（LangChain 的 `MultiVectorRetriever` 模式）。

```python
from doc_parsing import load_all, build_embedding_units

parents = load_all()                          # 1341 块，给 LLM 看的文本
units = build_embedding_units(parents)        # 10610 个单元，拿去嵌入
```

| 单元类型 | 数量 | 内容 |
| --- | --- | --- |
| `chunk` | 1341 | 整块，与父块一一对应 |
| `row` | 9269 | 表格的单行，中位数 112 字符 |

行级单元会把列名一并写进去，脱离表格后依然自解释：

```
五粮液 2024年报 | 第十节 财务报告 > 七、合并财务报表项目注释 > 1、货币资金 | 项目=银行存款 | 期末余额=78,907,591,498.82 | 期初余额=74,892,248,621.63
```

多层表头（`项目` 竖跨两行、`2024年末` 横跨两列）会被合并成复合列名：

```
... | 项目=货币资金 | 2024年末 金额=127,398,915,484.11 | 2024年末 占总资产比例=67.67% | 2024年初 金额=115,456,300,910.64
```

> 📌 约 **10% 的表首行其实是数据**——键值表（`股票简称|五粮液|股票代码|000858`）或表头缺失的续表。强行当表头会产出 `张庆=男` 这种垃圾，所以靠"首行是否含纯数字单元格"判断，没有表头就退化成纯值拼接。

## 🔬 技术选型说明

**用的是结构切分，不是语义切分。** 年报的章节结构显式且规整，这个信号比 embedding 距离可靠得多；语义切分要为每个句子调一次 embedding，成本不低；最关键的是它会切碎表格——相邻表格行的向量距离波动很大，容易被误判成语义断点。如果要引入，合理做法是只对"管理层讨论与分析"这类纯叙述章节启用。

**embedding 模型必须支持长上下文。** 实测（bge-m3 分词器）切块中位 530 token、最大 3212，**53% 超过 512**。`bge-large-zh-v1.5`、`m3e-base`、`text2vec` 这类 512 上限的模型会**静默截断**六成以上的块，不报错，只表现为检索质量莫名其妙地差。可选 BGE-M3（8192）、Qwen3-Embedding（32k）、jina-embeddings-v3（8192）。

**建议搭配稀疏检索。** 财报查询含大量精确术语（"货币资金"）和数字（"127,398,915,484.11"），稠密向量对这两者都不敏感。BGE-M3 单模型同时输出稠密和稀疏向量，不必另建 BM25。

**HTML 转 Markdown 不是 token 优化手段。** 字符层面标签占 67%，但实测 token 只省 17–34%——subword 分词器把重复标签压得很好，而展开合并单元格又会把省下的吐回去。所以表格保留 HTML 交给 LLM，嵌入走行级线性化。

**结构切分与 late chunking 可以叠加，但暂未启用。** 两者正交——late chunking 只改变*怎么算向量*（先整段编码成 token 级向量，再按边界池化），边界仍由结构切分决定。

当前实现有个具体障碍：late chunking 要求块是原文的**连续子串**才能映射 token 区间，而实测只有 4.4% 满足。破坏这个前提的恰恰是那些提升检索质量的增强——`CHUNK_OVERLAP=150` 的重叠、补回的表头、拼接的上下文前缀。要启用需要记录字符偏移、把"嵌入区间"与"展示文本"分开，并把 overlap 设为 0。

另一个约束是窗口：单篇年报清洗后约 32 万字符，而长上下文 embedding 模型上限 8192 token，装不下整篇，需要滑动窗口（约 40 个窗口/篇，每窗约 10 个块）。

上面的模板化上下文拼接是零成本的替代方案，先跑通管线再评估是否值得引入 late chunking。

## 🩺 体检

上面这些修复大多基于**硬编码假设**，换数据源时会失效，而且是**静默失效**——不报错，只是悄悄产出更差的切块。所以 `inspect_chunks.py` 每次运行都会跑一遍体检：

```
🩺 体检
   ✅ 缺页码元数据
   ✅ 表格缺表头
   ⚠️  元数据解析失败: 11 块 — 文件名不匹配 `公司+年份+年报`，跨年份过滤会失效
   ⚠️  私有区字符残留: 22 处 — U+F06C/U+F070 未映射，切分时会被静默删除…
   ✅ 超长块
   ⚠️  标题层级扁平: 11 块 — 编号体例未匹配，章节路径无法区分同名小节
```

各项对应的脆弱点：

| 体检项 | 什么情况会触发 |
| --- | --- |
| 元数据解析失败 | 文件名不是 `公司+四位年份+年报`。巨潮下载的原始命名 `贵州茅台2024年年度报告` 就不匹配 |
| 标题层级扁平 | 不遵循中文公文编号体例。英文报告的 `1.1 Overview`、港股年报、`1.1.1` 式编号都会退化成扁平 |
| 私有区字符残留 | 换用不同符号字体的 PDF，出现 `PUA_REPLACEMENTS` 未收录的字符 |
| 超长块 | 出现异常大的表格，有顶爆 embedding 上限的风险 |

> ⚠️ **PUA 必须在切分前检查。** `MarkdownHeaderTextSplitter` 会**静默吞掉**私有区字符——未收录的勾选框不是变成乱码，而是直接消失，`☑适用 □不适用` 变成 `适用 不适用`，选中项彻底丢失且不留痕迹。所以这一项跑在 `clean_markdown()` 的输出上，而不是切块上。
